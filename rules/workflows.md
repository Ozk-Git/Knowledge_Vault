# Workflows

AGENTS.md の操作定義の詳細手順。

## セッション開始

**トリガー**: 「セッションを開始してください」

1. `index.md` を読み、Vault全体の概要を把握する
2. 実ファイル数や更新状況が重要な場合は、`index.md` を鵜呑みにせず実ディレクトリを確認する
3. `log.md` の末尾5件を確認し、前回からの継続タスクを識別する
4. `log.md` の記録が不足している可能性があるときは、必要に応じて実ファイルやGit履歴も参照する
5. 以下の情報をもとに、今セッションで着手できる作業を優先度順に提案する（3件以内）:
   - `Inbox/` `Clippings/` の未処理件数（件数も併記する）
   - `#llm-draft` タグが2週間以上放置されているノート
   - `Papers/*/03_gaps.md` の未解決事項（`状態: 未着手 / 対応中`）
   - `log.md` の継続タスク
6. Probe を実行し、結果をセッション開始報告に含める
7. Vault の状況を報告する

## セッション終了

**トリガー**: 「セッションを終了してください」

1. `index.md` は派生サマリとして、必要な範囲で更新する
2. `log.md` は補助的な操作記録として、主要な変更・判断を追記する
   形式: `## [YYYY-MM-DD] {操作} | {内容}`
3. 今セッションで生まれた新しい問いや半形成のアイデアがあれば `Inbox/` へのメモ追加を提案する
4. 終了報告として、今セッションで行った作業の要点を3行以内でまとめる

## Ingest — ソース取り込み

対象: `Clippings/` の未処理ファイル、`References/` 配下の論文PDF・書籍、`Daily/` のメモ

ソースのタイプに応じてプロンプトを使い分ける:

- 論文 PDF（`References/papers/` 配下）: `templates/paperdesk-read.md` を適用する
- 自分の論文の査読シミュレーション: `templates/paperdesk-review.md` を適用する
- 書籍・その他（`References/books/` 配下 / `Clippings/` / `Daily/`）: `Literature/AGENTS.md` の標準手順に従う

## PaperDesk

PaperDesk のモード選択は、ユーザーの依頼の粒度に応じて判断する。
root `AGENTS.md` には概要のみを置き、詳細な実行範囲はここで管理する。

| モード | 用途 | 主な実体 |
|---|---|---|
| Mode A / read | 他者の論文1本を読解・Vault統合する | `templates/paperdesk-read.md`, `paperdesk-read` skill/agent |
| Mode B / review | 自分の原稿を投稿前に批判的評価する | `templates/paperdesk-review.md`, `paperdesk-review` skill |
| Mode C / survey | 複数論文を横断して調べる | `templates/paperdesk-survey.md`, `paperdesk-survey` agent |
| Mode D / evidence-check | 科学的主張の支持状況を素早く確認する | `templates/paperdesk-evidence.md`, `paperdesk-evidence` skill |

### モード選択の原則

- 個別論文が明示されている場合は Mode A を基本とする
- 投稿前原稿・査読シミュレーション・批判的評価は Mode B を基本とする
- テーマ、問い、分野、複数文献の探索は Mode C を基本とする
- 科学的主張・健康情報・研究上の仮説について「根拠があるか」「支持されているか」を確認する場合は Mode D を基本とする
- 「検索」「候補提示」だけが求められている場合は、候補提示で一度止める
- 「サーベイ」「整理」「ギャップ」「合意と矛盾」まで求められている場合は、必要な範囲で読解と統合まで進める

### Mode C — survey

Mode C はサブエージェント・オーケストレーターとして扱う。
内部で `paperdesk-read` サブエージェントを論文ごとに spawn し、文献景観を横断統合する。

ユーザーが「PaperDesk Mode C」「survey」「横断サーベイ」と依頼した場合は、サブエージェント・オーケストレーションの明示的依頼として扱う。

### Mode D — evidence-check

Mode D は科学的主張の根拠確認に使う。

主な使用場面:

- 「○○に科学的根拠はありますか？」
- 「この主張は論文で支持されていますか？」
- 「○○と△△の関係についてエビデンスを調べて」
- 「この記述を記事や原稿に入れてよいか、根拠を確認して」

基本方針:

- Consensus MCP を主入口として使う
- 必要に応じて PubMed / Semantic Scholar / Zotero で一次文献を確認する
- 結論は「支持される / 限定的 / 矛盾あり / 根拠不足」に分類する
- 医療・健康・投資など高リスク領域では、断定を避け、研究の限界を明示する
- Literature ノート作成や Ingest は自動では行わず、必要なら提案する

## Probe — 能動的問いかけ

セッション開始時に自動実行する。

- 最近 Ingest されたノートの中から、既存 Permanent ノートと矛盾・補完・拡張する関係を探し報告する
- `状態: 確定` の Claim のうち、証拠が薄いものを指摘する
- `#open-question` の中から、既存知識で答えられそうなものを提案する
- 長期放置の Permanent ノートを1〜2件取り上げ、最近の知識との接続を問いかける

## Remember — 議論の記憶保存

**目的**: セッションで決定した設計方針・背景・判断を Vault 内に保存し、端末・AI エージェントをまたいで再現性高く引き継げるようにする。

**手順**:

1. 現セッションの決定事項・設計方針・背景を整理する
2. 保存先を判断する:
   - 特定ディレクトリの作業に関する内容 → そのディレクトリの `context/` 内に保存（例: `Papers/slug/context/design-decisions.md`）
   - Vault 全体・複数ディレクトリにまたがる内容 → `rules/session-memory.md` に追記
3. 以下の形式で記録する:
   ```
   ## [YYYY-MM-DD] {トピック}
   ### 決定事項
   ### 背景・理由
   ### 今後の方針
   ```
4. どの AI エージェントでも解釈できる平易な Markdown で記録する（AI 固有の構文を使わない）
5. `log.md` に保存先と概要を記録する（形式: `## [YYYY-MM-DD] Remember | {保存先} — {概要}`）

## Connect — セレンディピティ探索

- 2週間以上前の Permanent ノートと最近追加されたノートの予期しない接続を探す
- 孤立ノート同士に潜在的な関係があれば提示する
- 提案は候補列挙にとどめ、採否はユーザーが判断する
